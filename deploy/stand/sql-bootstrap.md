# NEW dedicated stand SQL bootstrap

Refs [Backend169](https://github.com/UltiStatsDev/ultistats-backend/issues/169), [Backend168](https://github.com/UltiStatsDev/ultistats-backend/issues/168), [Web121](https://github.com/UltiStatsDev/ultistats-web-ui/issues/121).

This provider initializes only a newly created dedicated owned PostgreSQL16 cluster. It does not install host packages/services, create Docker resources, deploy a release, adopt an existing database, change human/auth runtimes or prove SQL fencing. Installer125 creates exact resources and invokes checked source;170 owns ongoing SQL maintenance/proxy validation. The existing restricted-login provider/policy stays unchanged.

## Identity and private descriptor

Logical installationId is exactly `ultistats_private`, under SQL-safe grammar `^[a-z][a-z0-9_]{0,31}$`. Separate `runtimeInstanceId` is lowercase12hex, explicitly bound to Docker resources and a private creation receipt. Neither is an API installation UUID; preauth247 has none. Fixed database is `ultistats_private`, migration owner `us_ultistats_private_migration`, service DML role `us_ultistats_private_service`, restricted login `us_ultistats_private_sql`.

`bootstrap-contract-v1.json` defines the interface. Each operation takes `{schemaVersion:1,installationId,runtimeInstanceId,databaseContainerId,databaseImageId,databaseVolume,databaseNetwork,creationReceiptPath,bootstrapReceiptPath,adminCredentialsPath,migrationCredentialsPath,serviceCredentialsPath,loginCredentialsPath}`. IDs are complete immutable64hex, image identity `sha256:<64hex>`. All four credential files are distinct owner-only0600 JSON `{password}`, printable ASCII20..256 characters, separate random passwords. File parents are real owner-only directories; symlink files/parents and group/world access are refused. Use trusted local paths outside Git, never HTTP/request-controlled executable or resource inputs.

The NEW creation receipt binds container/image/volume/network names, immutable IDs, Created timestamps, logical/runtime identities, PostgreSQL systemIdentifier (decimal string), and `emptyVolumeBeforeStart:true`. It records local volume/bridge network drivers. Installer must create and prove the empty volume before first PG start; a boolean for an existing volume is not acceptable provenance. Provider checks the live objects, new-cluster contents and exact receipt together. Named volume must use local driver without bind/foreign driver options; network is a dedicated internal bridge. Docker labels are `org.ultistats.installation-id`, `org.ultistats.runtime-instance-id`, `org.ultistats.resource-kind` with kind postgres/postgres-data/network/proxy/writer. Unknown network members, PG publication, extra networks and **every** PG mount beyond its exact named PGDATA volume are refused. No exported Unix socket, secret/config bind mount or host data adoption.

## Calls and phases

`await prepareSqlCluster(options)` verifies the new cluster contains only native roles/databases, no application objects/extensions/clients, then creates distinct migration/service roles with SCRAM verifiers. It creates the DB with migration owner and installation comment, removes PUBLIC rights from its own maintenance/template DBs, sets public schema ownership and service DML/sequence defaults, and installs initial HBA TCP deny-all. Complete matching preparation is idempotent; existing foreign/unknown role/DB collisions reject before initialization. Repeated calls verify exact migration/service role OIDs, markers, nonprivileged attributes and zero memberships as well as DB/system/container identity.

`await bindSqlSources(options,{proxyContainerId,proxyImageId,writerContainerIds})` observes actual owned container images/network addresses. Writer/proxy containers may be started in a controlled startup gate to obtain actual IP before accepting work. It writes exact /32 HBA: login only from proxy IP, migration/service only from explicit owned writer IPs. Output `serviceSources` remains `{role,address}`; typed `writerBindings` adds `{containerId,imageId,address,role}` per allowed role, separately from strict170 identity. Identical source binding is idempotent; changed members/IPs/config require explicit owner recovery, never an automatic rebind of live clients.

`await finalizeSqlCluster(options,{proxyContainerId,proxyImageId,writerContainerIds,application:{containerId,sourceCommit,jarSha256,jarPath:'/app/app.jar'}})` requires actual247 application source, live artifact hash, expected separate credential/user environment, actual V1–V9 Flyway history installed by migration owner, and observed service JDBC pool at its owned writer IP. It validates service CRUD in a rollback transaction, establishes service DML/defaults while denying Flyway-history mutation, invokes existing169 explicit frontend policy through a private owned-container psql adapter, and rechecks HBA before final receipt. Service gets no TEMP after finalization. Frontend policy receives no wildcard/future security grants.

Phase receipts are NEW_CLUSTER_VERIFIED → BOOTSTRAP_PREREQUISITES_APPLIED → SQL_SOURCES_BOUND → BACKEND247_MIGRATED_AS_MIGRATION_OWNER → SERVICE_DML_VERIFIED → ROLE169_RECONCILED → SQL_INGRESS_READY_FOR170. Last name means bootstrap prerequisites completed, **not** opened ingress, proved transaction quiet point, released170 fence, passed HTTP readiness or delivered an installation. Caller keeps proxy/HTTP ingress and credential delivery closed until all actual integration gates succeed. Any failure retains exact durable phase and data; never recreate/overwrite/restore to force green. Partial ambiguous state or leftover exclusive operation lock requires explicit verified owner recovery, no TTL replay. Complete repeat still checks live identity and HBA rather than returning a stale ready flag.

## Actual247 configuration and secrets

Prepare roles/defaults first, bind exact writer sources, then start immutable247 artifact with `DATABASE_URL`, `DATABASE_USERNAME=us_ultistats_private_service`, `DATABASE_PASSWORD`, `SPRING_FLYWAY_USER=us_ultistats_private_migration`, `SPRING_FLYWAY_PASSWORD`. Migration and datasource credentials are separate; [Spring Boot3.5 property documentation](https://docs.spring.io/spring-boot/3.5/appendix/application-properties/) documents the Flyway credentials, and the integration test verifies actual247 behavior against real PostgreSQL. Product code/DTOs/migration files are not changed.

Backend admin transport is trusted Docker exec **as OS user postgres** and local PostgreSQL peer authentication. This requires only existing Docker authority, no host psql package or exported socket. Nonadmin local installation roles use SCRAM; all unlisted local/TCP access rejects. HBA is written/reloaded inside owned PGDATA, checked with actual parse/hash/source evidence. [PostgreSQL HBA documentation](https://www.postgresql.org/docs/16/auth-pg-hba-conf.html) describes rule ordering and diagnostics; [default privileges documentation](https://www.postgresql.org/docs/16/sql-alterdefaultprivileges.html) explains why migration-owner defaults must be explicit.

Passwords/verifiers never enter subprocess argv, public receipts/status, Git or public logs. Docker initialization/application credentials can use private host `--env-file` filenames; secret values must not be arguments. Bootstrap sends SQL through private child stdin, suppresses child diagnostic output, derives SCRAM verifiers locally, and atomically fsyncs private0600 journal. Existing169 adapter uses peer admin and private transient host pgpass; no PG mount is required. Actual credential files, Docker inspect environment and failure/recovery logs stay private. Receipt binds bootstrap source/contract, original role source/policy and application baseline hashes without credentials.

## Verification and resource lifecycle

```sh
node --test deploy/stand/tests/sql-bootstrap.test.mjs
bash deploy/stand/tests/run-sql-bootstrap.sh
```

Source-only command explicitly skips PG without fixture. The full runner owns its bounded heavy lock; do **not** wrap another heavy lock. It requires Node22, Git, Docker, tar/flock and JDK21 (`JAVA_HOME`) for default exact247 build. It archives exact247 Git source, builds bootJar under JVM lock, uses its original Dockerfile final stage and pins resulting image/JAR identity. Optional `BOOTSTRAP_APPLICATION_IMAGE=sha256:...` and `BOOTSTRAP_APPLICATION_JAR_SHA256=<64hex>` select an independently proven immutable247 code artifact for local verification without rebuilding or retagging it.

Every run writes an exact NEW namespace resource plan before creating its local volume/internal network/PG/application/SQL-client fixture. No host ports are published. The SQL-client helper tests source authentication; it is not a PgBouncer/fencing substitute. Tests verify actual247 API writes through service account, actual Flyway owner history, frontend CRUD and deniedDDL/admin/foreign/history/future-security access, collision/private-file/partial-state/role-drift/HBA changes and idempotence. Child API logs/private identity evidence are retained without publishing credentials. After sole consumer END the runner removes only exact owned containers/network; named data volume, source artifacts and private evidence remain. No global prune, -v, foreign cleanup or human/stable/auth target reuse. Source readiness is separate from shared QA/PO and actual stand delivery;169/168 stay OPEN.
