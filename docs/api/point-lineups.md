# Edit a confirmed next point lineup

Public GET `/api/v1/matches/{matchId}/point-lineups` gives the canonical points and journal revision. If `nextLineupEditsWriteEnabled` is true, staff can edit the confirmed point whose status is `NEXT` and whose `pullEventId` is null. False means the server supports edits with point lineup writes disabled. A missing field means the server does not advertise the edit contract.

Use the existing PUT `/api/v1/matches/{matchId}/point-lineups/{pointId}` with `SPORTS_WRITE`, CSRF and the journal's existing `X-UltiStats-Point-Lineups` capability. The body carries both match teams with their ordered entries, the snapshot's `logRevision` as `expectedLogRevision`, and the confirmed lineup's `revision` as `expectedLineupRevision`. Both revisions are nonnegative JSON integers in the int64 range. Omit `expectedLineupRevision` for the original confirmation flow. Explicit null is invalid in edit mode.

Entry requirements are the same as for confirmation. Include each match team once. Each team may have zero to `playersPerTeam` entries. Known players must be unique match roster players on their own team. Temporary slots use unique match-scoped IDs and team-local numbers from 1 through `playersPerTeam`. A retained slot keeps its team, number and existing identification even when reordered. An archived incoming reserve still owns its ID and number. A slot with any event reference (including undone events) or identification cannot be removed.

A change returns 200 with the same point ID and the lineup revision incremented by one. The server keeps the journal revision, score, other points and original confirmation timestamp. Portable export uses the resulting selection in the existing format. An identical selection at the current revision is a no-op. With the same journal base, the same selection at the immediately previous confirmed revision also returns 200 with the current lineup. Other stale edits, including a different selection competing at the same base, receive a conflict. The edit gate and NEXT check also apply to no-ops and retries.

A stale journal base returns 409 `EVENT_LOG_STALE`. A noncanonical, unconfirmed or no-longer-NEXT point, a conflicting lineup revision, or an edit blocked by stored actor history returns 409 `POINT_LINEUP_CONFLICT`. Disabled writes return 409 `POINT_LINEUP_WRITE_DISABLED`. Invalid bodies or selections return 400. After a conflict, refresh the public snapshot before deciding whether to submit another edit.

## Correct a known starter on a completed point

The public point-lineups snapshot advertises the protocol with `starterCorrectionsWriteEnabled`. Its value follows the point lineup write flag. Use the snapshot's `logRevision`, the selected completed point's `lineup.revision`, and its `closingEventId` to build the request.

Send the same JSON body to POST `/api/v1/matches/{matchId}/point-lineups/{pointId}/starter-correction/preview` and PUT `/api/v1/matches/{matchId}/point-lineups/{pointId}/starter-correction`. The required fields are `expectedLogRevision`, `expectedLineupRevision`, `expectedClosingEventId`, `fromParticipantId`, and `toParticipantId`. The revisions are nonnegative int64 integers. The two participants must be distinct known players on the same roster snapshot team, with the source in a confirmed initial PLAYER entry. Both calls require `SPORTS_WRITE`, CSRF and the existing `X-UltiStats-Point-Lineups` capability for journals with substitutions or introduced reserves.

The preview returns `pointId`, `teamId`, the zero-based `entryIndex` within that team's initial entries, both participant IDs, a `boundary` with `eventId` and `kind`, and an ordered `changedEvents` list. Each change includes `eventId`, `type`, and `sides`. `FROM` denotes `participantId` for one-player events. The boundary is `OUTGOING_SUBSTITUTION` at the source player's first actual exit, where only `FROM` can change, or `POINT_CLOSE` at the closing event. An empty change list means only participation will change.

PUT recomputes the preview under the match write lock and returns `correction` (the applied preview), `point` (the canonical updated lineup), and the new `logRevision`. Both revisions advance once, including for a participation-only change. Event IDs, types, order, occurrence times, scores, and adjacent points are preserved. Journal reads return corrected actors. Old receipts that depend on the superseded journal fail with a conflict.

A stale log returns 409 `EVENT_LOG_STALE`. A stale lineup or closing event, an ineligible pair, overlapping participation, or an invalid replay returns 409 `POINT_LINEUP_CONFLICT`. A replacement may appear later as a raw PLAYER after leaving at the correction boundary, provided the suffix replays. A player already identified as an initial temporary actor or active introduced reserve cannot take the corrected starter entry. The portable lineup requires distinct identified players across those entries. If the outgoing starter pulled and a later BRICK refers to that original puller, the correction conflicts because preserving the BRICK reference would break its connection to the corrected PULL. Neither preview nor save changes state on conflict. Refresh the lineup and journal before submitting a new proposal.
